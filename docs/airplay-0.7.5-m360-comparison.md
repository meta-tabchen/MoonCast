# 0.7.5/code63 与 Mirroring360 的当前对照

目标是电视持续播放。用户已确认 code62 比例正常；电视退出后回到**系统桌面**，手机仍显示连接。这并不能证明接收进程崩溃，也不能仅靠手机状态修复判定问题解决。

M360 证据沿用主任务提供的 DEX/x86_64 静态复核，具体地址和证据限制见 [code61 历史审计](airplay-code61-m360-audit.md)。本 Mac 没有完整 M360 APK/ELF 样本及哈希，未独立复跑反编译；目标 ARM 分支和实际网络序列仍未验证。没有复制第三方密钥或受保护代码。

## 本轮证据

- code62正常化源码哈希 `f3d4e1d3c052da37f62ebfbda358e3f6b1e88d8c4aa0c48d4ff95d5c0baf5c09` 上，新增AVCC用例从首NAL长度256起失败；修复后276项H.264/归属检查通过。
- 有效300字节userdata SEI加真实20帧视频：正常化结果与独立构造的Annex B字节完全一致，经过原生7100模拟接收后仍能独立严格解码20帧。
- 已有原生构建取回的600秒测试：11989视频包、599心跳、60配置；接收端关闭和25帧新连接通过，总计独立解码12014帧。NTP48和RAOP32各2382次请求应答。三种尺寸，约两分钟有界历史，无长度错误/回退PTS/B-slice/解析错误。fixture有200次keyflag与实际IDR不一致，实际NAL判定仍正常，计数已保留。
- Mac上的TCP_INFO明确不可用；Android实现已编译，目标内核读取效果未实测。以上均为主机证据，**不是目标电视验收**。
- 完整Java脚本仍在已有OriginalMediaServerTest因Connection reset停止；其余六组单独通过。保留失败，不称全量测试通过。

下一次目标复现最小证据：电视回桌面时，在手机仍连接的状态下立即复制投屏诊断，并记下约多少秒退出。若编码、NAL和PTS正常且ACK仍前进，再对照同手机M360完整连接验证接收端活动和额外控制；若出现明确码流异常，先做一个变量的修复/对照。没有把本轮AVCC缺陷称为该电视退出根因。
