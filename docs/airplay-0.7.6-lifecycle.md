# 0.7.6/code64：升级后连接生命周期

用户确认最终0.7.5/code63仍失败。正确时序是：**电视先返回系统桌面，随后手机FPS从二十多降到两帧多**。因此后续掉帧不能作为电视退出的先因。本轮不更改编码器、level、GOP、PTS、比例、采集或音频；五个视频相关源码文件与已交付code63逐字节相同，code62正常比例保留。

## 已复现的缺陷与修改

1. **把读侧EOF当成整个媒体连接关闭。** 旧Watch在升级后读HTTP响应，遇EOF/UnexpectedEOF即关闭TCP和7010。真实TCP用例中，对端仅CloseWrite、仍继续读取媒体，我们却在约0.33秒内主动关闭媒体。TCP两个方向可独立关闭，见 [RFC9293 §3.6.1](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6.1)。M360已提供的静态链路在POST后只写，不额外监测响应EOF；它不会由此关闭媒体。这是明确实现差异，但**尚未证明目标电视发出了这种FIN**。

   新Watch先Peek一个字节，区分裸FIN与已经开始但截断的HTTP响应。裸FIN只记录peer-send-ended并结束读侧监测；视频、心跳和计时继续。写失败、RST、三秒写超时、用户停止仍清理会话。不能简单忽略所有UnexpectedEOF，因为那会漏掉截断的HTTP消息。

2. **拒绝头被未结束的响应体阻塞。** 旧Watch先读取/关闭响应体，再检查状态。503头已到、Content-Length声明64但正文未到时，错误不会及时报告。新实现看到非2xx头立即以结构化HTTP状态失败，先关连接再关闭Body；成功响应的截断/超大正文仍失败，不忽略认证拒绝，不回退加密。

3. **旧内存诊断盖过较新的退出报告。** 原复制按钮只要内存非空就不读文件，可能复制退出前的failure=none。新报告带快照单调/墙钟时间；复制时选较新的有效快照，显示service-cache/private-store、reportAgeMs、copiedElapsedMs。无时间戳或疑似旧启动/时钟变化的报告标unknown，不能被当作当前会话无错误的证明。未改变手机连接状态来宣称电视恢复。

## 新增观测

- controlRead：读侧状态、裸EOF时间、响应计数、最后HTTP状态、结构化错误。
- heartbeatTiming：首次、最近一次成功心跳时间与最大间隔，调度和包内容不变。
- timingPeer：所选接收端IP的入站包数、被忽略格式数、最后长度/低三位、最近到达时间。48字节NTP与32字节RAOP应分别解释；不输出IP或原始数据，不向无效格式应答。非所选IP仍按原规则过滤，0计数不代表整个网络无UDP。
- code63已有SPS/NAL/IDR/PTS、TCP_INFO和约两分钟有界历史继续保留。

## 当前证据能区分什么

| 观测 | 可以说明 | 不能说明 |
|---|---|---|
| 裸读侧FIN后仍收视频 | 对端结束发送方向，写方向仍可用 | 电视画面仍在显示，或接收进程存活身份 |
| 非2xx响应 | 接收端明确拒绝/结束该HTTP操作 | 接收端为何作此决定；需状态码与接收端证据 |
| 写/RST/超时 | 媒体发送方向不可继续 | 是正常退出、进程崩溃、网络变化中的哪一个 |
| TCP ACK仍前进、画面已回桌面 | TCP对端仍确认数据 | 解码/渲染成功、Activity或进程未退出 |
| 7010绑定且0请求 | 没有被计入的所选端有效请求 | 时钟就是退出原因；需区分无包、格式忽略、源IP过滤 |
| 快照failure=none | 该来源、该时间的报告未记录失败 | 电视没有退出，或旧报告就是退出后的结果 |

返回系统桌面不能仅凭TCP事件区分Activity结束、接收进程退出或会话主动结束。仍缺目标code63退出前后的完整诊断、接收应用身份/大致秒数，必要时需要目标接收端进程退出日志或同手机M360连接对照。没有将模拟接收端当作目标电视。

## 针对性验证

- 保存修改前半关闭与503正文阻塞的失败日志；修复后真实TCP半关闭仍接收视频/心跳。
- 截断状态行、头和成功正文仍失败；Digest、认证必需、FairPlay不降级、连续CTR与阻塞写界限回归通过。
- 无效计时格式无应答，但与“完全没收到所选端包”可以区分。
- 快照单测覆盖新退出文件优先、较新内存优先、无时间戳旧报告、启动/时钟/未来时间及空状态。
- 持续回归设置为接收端第30秒发FIN后继续收媒体，共180秒，再完整关闭和新连接；结果与最终APK核验记录在本checkout旁evidence-0.7.6，不能转写为电视验收。
- 完整Java脚本仍在已有OriginalMediaServerTest发生Connection reset；保留非零状态，补跑其余测试组。不称全量Java通过。

网络研究的 [UxPlay #328](https://github.com/FDH2/UxPlay/issues/328) 是收包持续但sink/QoS丢帧的案例；[#207](https://github.com/FDH2/UxPlay/issues/207) 涉及设备睡眠、接收端时基/同步。它们是背景资料，不是这台电视返回桌面的根因证据。未据此切换时钟或乱调编码参数。
